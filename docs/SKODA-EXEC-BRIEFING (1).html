1 The ask, in one view

The 15 Oct demo is mission-critical and politically sensitive. Per Škoda: the team must show value with AEM by this date, "or this project and all future AEM projects are in jeopardy." Everything below is organised around making that date achievable — and it is achievable, but it's tight and starts now.
  1. Two fixed dates. A functioning demo by 15 Oct 2026 (front end working, approved AEM Assets, blog posts + media-cart replicated) and go-live 2 Jan 2027 (content fully migrated, authoring workflows running).
  2. This is the blueprint. Škoda intends this project as the template for future VW EDS projects — so it must be done cleanly and be reusable, not just "demo-ware."
  3. What it takes. A focused ~4–6-week build to the demo depending on team size (§8; staff to maximise value — 4 engineers, ~4–5 weeks), delivered AI-led / human-steered (the AI builds the bulk; a small team each owns a workstream, with one acting as lead — accountable for quality, integrations and the date). The technically hardest parts have a defined, tested approach (§6).

Technical complexity: moderate and well-understood — favourable for Edge Delivery. This is a content/editorial site with none of the hardest categories: no commerce, no personalization, no user logins, no dynamic media. The one dynamic piece is the media-cart's zip-on-demand, which needs a single small serverless function (§5) — modest, and the only such component. The work is scale plus a few well-defined back-end features — a far simpler undertaking than a comparable AEM Sites or commerce build. The schedule, however, is tight (§10): the challenge here is the fixed, immovable date, not technical difficulty. The demo is a deliberate, focused slice of the whole.

  • A handful of repeatable page templates (press release, story/blog, page, encyclopedia, listings) and ~10 content blocks + ~5 site-wide elements.
  • Search & filtered listings run across 15 topic facets.
  • Navigation placement is driven by metadata tags (matches Škoda's note).
Media, video & environment
  • Images sit on S3 + CloudFront as a plain cache — no on-the-fly transforms, no Dynamic Media today (confirms Škoda's note). EDS's image pipeline will be an upgrade.
  • Video = Vimeo / YouTube embeds — no self-hosted video, no MAM (confirms Škoda's note).
  • No user login, no personalisation, no edge functions in use today (we add one small serverless function for the media-cart zip — §5); authors sign in via Škoda's IDP.
  • Header/mega-menu & footer are plain nested menus — low build effort.

6 Settled facts in our favour

Established points that keep the build straightforward.

Blog posts are built from a small, consistent set of components, and that set is the same in English and Czech — so adding Czech is more volume, not more complexity.
Media-cart needs no account
Device-ID based, no login/account. The zip-download is the one piece Edge Delivery doesn't do natively — it needs a small serverless function (net-new for Škoda), which builds the zip, stores it, and returns a short-lived link. Host to confirm in a spike (Adobe App Builder, a CDN worker, or client-side zip in the browser each work with the right pattern — §9). Fallback: a per-story pre-built "download all" bundle.
Approved assets source = AEM Assets
Approved images are intended to come from AEM Assets. Open: whether Škoda has its own instance, uses a shared VW/group one, or needs one provisioned — and whether the images are in it yet (§9). Demo fallback: serve approved images from the content pipeline and cut over later.
Video = no migration
Vimeo/YouTube embeds mean no video files to move, transcode or host, and no video player to rebuild.
Header/footer are plain nested menus
Standard navigation lists, not an elaborate mega-menu — low build effort.

7 Timeline & how we deliver

M1 — Demo · 15 Oct 2026 (~4–6 weeks, by team size — §8)

What we deliver, working, on the day:

  • Front end working — core blocks + navigation
  • Blog / story pages replicated
  • Media-cart (collect → zip-download)
  • Search & filtered listings
  • AEM Assets integrated (approved assets available; not necessarily all in active use by the demo)
  • Consent + analytics (OneTrust / GA / FB pixel) — scope for the demo to be defined; may be deferred to go-live
  • English + Czech
  • A Figma-to-AEM showcase

Not in the demo: full content archive, the four on-demand languages, embargoes, banners/newsletter — all M2.

M2 — Go-live · 2 Jan 2027

Everything else, for the live site:

  • Full content migration
  • Authoring workflows + Škoda IDP
  • The four on-demand languages (DE/SK/SR/SL)
  • Content embargoes (staged-publish)
  • Banners / newsletter — per decision
  • Analytics finalised; Adobe-recommended CDN
Delivery model: AI-led, human-steered. The AI builds the bulk — blocks, the flattener, import, listings, media handling — compressing the code-heavy work. The roles around it:
  • Engineers (§8) — each owns a workstream: steers the AI, integrates and verifies it. One acts as technical lead, accountable for the overall outcome and the cross-cutting integrations (AEM Assets, consent/analytics, media-cart). Lead is a role within the team, not a one-person build.
  • QA — owned, ~half a role for the demo. Quality is continuous (each engineer verifies their own workstream, browser-checked) plus a final QA gate before sign-off. For the demo this is a dedicated ~0.5 FTE QA owner — a distinct person accountable for a11y, performance, and cross-page consistency, ramping up as integration begins (a ~4–6-week slice doesn't need a full-time QA, but it does need an independent one). Why it matters here: on a fixed demo date the real risk is "built, but something looks off on stage," and much of our current confidence is analysis-based, not yet browser-verified — so an independent set of eyes pays off. At go-live we'd scale QA to full-time, and add an accessibility specialist if WCAG 2.1 AA is contractual.
  • PM (part-time, organisational) — runs the logistics: schedule, access chasing, status, decision tracking, and the Škoda interface. Not the project lead — coordination and admin, so the engineers stay on the build.

The ask of Škoda: a named technical counterpart, access (AEM Assets, repo/authoring org, IDP & analytics specs), and the demo content set — all ready by demo build start. This is client-controlled and, on a fixed date, our single biggest schedule dependency (tracked as a High risk in §10).

8 What runs in parallel — and the value each added engineer delivers

Parallelism isn't "one workstream per person" — the work groups by how it can be split. Three shapes decide how much each added engineer delivers: a gate that must finish first, a divisible pool that any number of engineers can share, and a few dependency chains that must run in order — all feeding one integration funnel.

The engineer profile matters as much as the count. These are senior front-end developers fluent in the Adobe ecosystem — Edge Delivery Services, App Builder, and Experience Workspace — who are practised with the AEM modernization agent and AI-based development flows (the model that makes the ~4–6-week timeline real). Just as important as the tooling: each must be ready to own their outcome end-to-end and find a way to make it happen under a fixed date. This is a small senior team, not a large junior one — the timelines below assume that calibre.

The engineer counts above are the build lanes. In every case, add a part-time PM (organisational — schedule, access, status, Škoda interface), a dedicated ~0.5 FTE QA owner (continuous + a final gate, §7 — scales to full-time at go-live), and a Škoda counterpart. Design is not a delivery lane — Škoda's Figma design system is provided and migrated as-is, so no designer is on the critical path; the Figma-to-AEM showcase is engineering work. Elapsed times spread the demo effort estimate (~40–66 AI-assisted engineer-days) across the build lanes — not a clean divide: adding people trades calendar time for a modest rise in total person-days (coordination overhead), and the Foundation → content-chain → integration floor caps the gain, which is why 4 engineers lands at ~4–5 weeks, not proportionally faster. More people never means less total effort. Planning-level, not a quote.

Recommendation: staff to maximise delivered value — 4 engineers. The goal for a mission-critical, politically-charged demo is the strongest result on the day, so the question isn't "cheapest team" — it's "how much value does each added engineer deliver." Every added engineer converts directly into value: a shorter build, a bigger buffer against the fixed date, more polish, and a richer Figma-to-AEM showcase. 4 engineers (~4–5 weeks) delivers the most — the blocks pool splits, the interactive chains and content chain all run at once, and the showcase gets its own lane. 3 engineers (~5 weeks) is the solid baseline where everything still runs concurrently with real buffer. 2 engineers (~6 weeks) is feasible but leaves little margin — one person carries both the blocks pool and a chain. The only ceiling is the Gate → Content-chain → Funnel floor: beyond 4 engineers, added people no longer shorten the critical path, so that's where the value curve flattens.

9 Open decisions

Points to settle before or early in the build. Each is tagged with who owns the call — Škoda to decide, or Joint (Škoda + delivery team together). Resolving these — or naming an owner and a date — unblocks the plan.

  • Embargoes Joint Confirm the staged-publish approach for confidential media-room items (authors preview; auto-publish on the release date) — this fits EDS and needs no special infrastructure.
  • Analytics Škoda Is Google Analytics + Facebook pixel + SEO metadata sufficient, or must a bespoke tracking layer be reproduced? (Affects effort.)
  • Figma showcase Joint Which 1–2 components should demonstrate Figma-to-AEM at the demo?
  • Banners & newsletter Škoda In or out for go-live? The banner tool is a full per-market ad platform — confirm it's wanted vs. a simpler promo.
  • Assets — is there an instance? Škoda Does Škoda have an AEM Assets instance at all? Three paths: (a) Škoda's own instance — cleanest end-state, but provisioning + licensing has procurement lead time; (b) a shared VW/group instance — likely faster if one exists, but raises tenancy / permissions / governance questions; (c) no instance in time — for the demo, serve approved images from the content pipeline and cut over later. Needs an answer before demo build start (demo-critical, §10).
  • Assets — where are the images? Škoda If an instance exists: are approved images already in it, or does the current site hold the originals? Sets the asset-mapping approach (likely a mix); if not in Assets, we import approved originals into the content pipeline.
  • Zip hosting Joint The media-cart zip needs a small serverless function — a net-new capability for Škoda (none in use today, §3). Host to confirm in a short spike: candidates are Adobe App Builder, a CDN/edge worker, or client-side zip in the browser — each has trade-offs (e.g. App Builder caps an action's direct result at 1 MB, so a zip must be written to storage and returned as a link, not inline). All are workable with the right pattern; we validate and pick early. Go-live ownership/hosting is the follow-on decision.
  • Content scope Škoda Full archive at go-live, or content from a cutoff date forward?

11 Recommendation

Proceed, and start immediately. The analysis is thorough, the hardest part has a defined, tested approach, and the demo scope is a credible, focused slice that doubles as the VW blueprint. The 15 Oct date is achievable with an early start, parallel workstreams, and the AI-led / human-steered model.

To close today: agree to proceed; name the Škoda counterpart and grant access; pick the demo content + Figma-showcase components; settle the open decisions in §9 (or name an owner + date for each); and confirm the engineer headcount (§8 — we recommend 4, to maximise delivered value).
